# PROJECT-INITIALIZATION V1.1.3 — Change Proposal Revision 2

Status: PRE-IMPLEMENTATION AUDIT INPUT
Builder Authorization: NO
Baseline: V1.1.2 remains frozen and must not be modified by this proposal.

## 1. Purpose
V1.1.3 is a targeted hardening release based on Production Validation #01. It is not a V2 redesign.
The goal is to close four observed P1 classes while preserving the validated V1.1.2 architecture and minimizing new machinery.

## 2. Blocking remediation targets
1. Clarification Evidence: every material clarification must link QUESTION → USER ANSWER / EXPLICIT DEFAULT DELEGATION → DECISION → STATUS → affected gates/artifacts.
2. Evidence / Path Closure: deterministic disk truth, explicit scope, ignore policy, origin classification, missing-path and unexpected-artifact detection.
3. Environment Provenance Completeness: required observations use deterministic statuses; required UNVERIFIED cannot PASS.
4. Final Verification / Freeze: Builder stops writing, deterministic freeze is established, verification is side-effect free, and post-freeze drift fails.

## 3. Clarification semantics
Clarifications are BLOCKING or DEFAULTABLE.
User silence is never ACCEPTED_DEFAULT.
ACCEPTED_DEFAULT is legal only when the user explicitly accepts the proposed default or explicitly delegates DEFAULTABLE decisions.
Destructive, security, architecture, overwrite, and protected-preexisting decisions cannot be silently delegated.
Classification is deterministic: a clarification is BLOCKING when it can change scope, filesystem or path contracts, ownership, required environment, acceptance/evidence gates, recovery, authorization, protected-preexisting handling, security, destructive/overwrite behavior, or any decision that is not safely reversible. A clarification is DEFAULTABLE only when none of those conditions applies and the exact default and delegation scope were approved before use. Ambiguity classifies as BLOCKING. The classification inputs, result, rule version, and hash are evidence.

## 4. Scope, Ignore, and Origin
Before build, freeze explicit Scope Spec and Ignore Spec and anchor their canonical byte hashes in an append-only location outside the audited root and Builder-controlled workspace. BUILD cannot start without those anchors. Any later change invalidates the existing BUILD authorization and requires the Contract Change Procedure and a new pre-BUILD anchor; an in-place post-BUILD replacement is never accepted as continuity.
Every relevant filesystem object must classify as PREEXISTING, MANAGED_GENERATED, or EPHEMERAL_IGNORED.
Unclassified in-scope objects are unexpected artifacts.
Ignore policy cannot be broadened after anomalies appear; post-approval scope/ignore mutation must be detected.
Before BUILD, also freeze an Existing-State / Origin Registry and an Approved Materialized Registry. For Clean Root, the canonical actual materialized state must equal the Approved Materialized Registry exactly. For Dirty Root, retained PREEXISTING objects remain distinct from approved materialized objects and the V1.1.2 Dirty Root conditions continue to apply.

## 5. Freeze and deterministic evidence
Freeze must have a machine-verifiable anchor, not an agent declaration.
Content hashing uses SHA256 over raw bytes: no CRLF/LF, encoding, Unicode, whitespace, trim, or formatting normalization.
Canonical paths are relative and use "/" separators; manifests and evidence records use one specified canonical JSON serialization, UTF-8 without BOM, LF termination, stable field representation, deterministic ordering, lowercase SHA256 hex, and an explicit genesis value. The evidence chain head is independently anchored outside both the audited root and the evidence-log storage so replacement of the whole log is detectable.
Freeze snapshots A and B cover the same resolved audited root and the same complete object/metadata fields. Manifest generation occurs outside that root, the freeze manifest is the canonical serialization of Snapshot B, and an exhaustive A/B add-delete-modify/type-mode-symlink diff must be empty.

## 6. Verification clean-room
Verification must produce zero protected-project side effects.
Temporary files, caches, logs, and generated verification artifacts belong outside audited scope or in predeclared EPHEMERAL_IGNORED locations.
After tests, freeze integrity must be rechecked.

## 7. Builder / Auditor separation
Builder implements and remediates findings.
Auditors are read-only and do not fix, commit, push, or delegate the audit back to Builder.
Findings flow: Auditor finding + evidence → Builder remediation → new evidence/freeze → independent re-check.
The approved Validator identity comes from a Human-approved registry outside Builder control. An audit must observe the real resolved audited root through an enforced read-only view or a before/after guard over that same root; a detached copy alone cannot prove the audited root was unchanged.

## 8. Remediation control
Use structured remediation tickets with Finding_ID, Severity, Rule_Violated, Affected_Path, Evidence_Path, Expected, and Actual.
Maximum blocking re-audit remediation loops, failed Validator cycles, and failed Production Validation cycles are each finite and contract-defined. Reaching the applicable limit escalates to Human and stops automatic work; do not auto-fix or re-run indefinitely.

## 9. Required regression coverage
V1.1.2 RT-01 through RT-24 remain unchanged, retain their identifiers and PASS/FAIL semantics, and are all mandatory.
RT-25 Clarification evidence and unresolved/default semantics.
RT-26 Evidence/path closure and unexpected artifact detection.
RT-27 Required environment provenance completeness.
RT-28 Freeze/final-verification drift and post-freeze mutation.
RT-29 Dirty Root + protected PREEXISTING drift under Freeze.
RT-30 is the cross-case runtime test proving the rules work together rather than only in isolation.

## 10. Preserve from V1.1.2
Preserve Existing-State Preflight, Clean/Dirty Root handling, Authoritative Inventory, Preexisting File Protection, PROVISIONAL semantics, Drift Detection, Provenance, authorization boundary, role separation, regression tests, and evidence audit unless an approved contract change explicitly supersedes a rule.
The V1.1.2 baseline and its canonical inventory/hash anchor are immutable, read-only, and external to the V1.1.3 candidate, verification workspace, and evidence log. V1.1.3 must compare against that pre-existing anchor and must never regenerate it from V1.1.3 state.

## 11. Complexity constraint
Do not introduce a full multi-agent framework, task scheduler, AWS-style team architecture, or large orchestrator merely to satisfy this release.
Prefer the smallest deterministic mechanism that closes a demonstrated gap.

## 12. Release intent
V1.1.3 must prove its rules through deterministic validation and independent evidence.
Principle: the agent does not earn PASS by saying it did the work; the evidence must prove the work was done.
FINAL_PASS is a necessary-and-sufficient machine predicate whose atoms, statuses, and failure mappings are defined by the Execution Contract; it preserves every V1.1.2 blocking gate and error meaning. A Release Candidate has a canonical protected manifest and identity hash binding the frozen candidate, approved contracts, Validator, evidence chain head, audits, and Production Validation evidence; any protected change creates a different candidate.
Implementation is prohibited until Proposal Revision 2 and Execution Contract V1.1 pass Independent Pre-Implementation Audit with zero blocking findings.
