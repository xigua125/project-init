# V1.1.4 Validator Procedure V1.0

Status: OPERATIONAL SPECIFICATION — SUBORDINATE TO V1.1.4 EXECUTION CONTRACT V1.3

This procedure implements existing Validator requirements. It is not a contract amendment and does not add or change a `FINAL_PASS` atom, regression test, authority, error vocabulary, cycle rule, evidence-record field, release-candidate field, or frozen semantic.

## 1. Governing authority

The governing authority remains `references/v1.1.4-execution-contract-v1.3.md`:

- Section 12 governs Validator identity, registration, approval, scope, and integrity.
- Section 13 governs evidence records, the append-only evidence log, and chain-head anchors.
- Section 17 governs validation/remediation counters and `ESCALATION_TO_HUMAN`.
- Section 18 defines RT-01 through RT-38 without renumbering, aliasing, replacement, or RT-39.
- Section 20 protects frozen and historical baselines.
- Section 23 governs Production Validation and its independent scenarios/counters.
- Section 24 governs RC/Stable fields and Human promotion authority.
- Section 28 is a dependency and authority summary, not strict wall-clock chronology.

Validator registration and Human approval are PRE-BUILD for the authorization they govern. Validator execution and its result are POST-BUILD. Registration never validates Builder output; execution never creates, approves, activates, or replaces registration.

## 2. Role separation

- Builder implements and self-tests. Builder cannot register, approve, activate, replace, or self-authorize the Validator.
- Human Project Owner is the Validator Registry Approver and Custodian for this implementation lineage.
- Independent Validator/Auditor executes under an identity separate from Builder and produces only independent validation/audit artifacts.
- Validator PASS does not grant Independent Audit PASS, Final Audit PASS, PV PASS, RC, Stable, or Human implementation authorization.
- `validator-self-test.mjs` and all of its output are `NON_AUTHORITATIVE`.

## 3. Required placement

Canonical Validator results and working state are external to every audited root. Registry and independent anchors are outside the audited root, Verification Workspace, evidence-log storage, and Builder write authority. Existing historical, failed, remediation, PV, authority, and passed-RT locations are immutable inputs only.

The approved control-plane root for the first implementation lineage is:

`C:/ProgramData/HermesProjectAnchors/project-initialization/v1.1.4-validator-01/`

Its planned children are `baseline/`, `registry/`, `authorization/`, `evidence/`, `results/`, and `anchors/`. Directory location alone does not establish independent custody.

## 4. PRE-BUILD identity and authorization sequence

1. Capture a complete pre-implementation manifest of protected governing files and the authorized change set.
2. Record Builder-created capture material truthfully as `BUILDER_CAPTURED_NON_AUTHORITATIVE` until independently approved and anchored.
3. Finish `validator.mjs`; compute raw-byte SHA-256. This exact hash is `validator_sha256`.
4. Human Custodian creates and approves an ACTIVE `validator-registry.json` entry containing all Section 12 fields.
5. Canonicalize the Registry under Section 9, hash its exact stored bytes, and store its independently approved anchor outside Builder write authority.
6. Issue an execution authorization record that binds the applicable registry/anchor, lineage, branches, roots, scope, evidence, and cycle.
7. No Validator execution is authoritative until independent custody and Builder-write exclusion are verified.

Post-BUILD registration, if ever needed, follows Section 12 and is prospective only. It cannot reopen, amend, validate, or upgrade an earlier execution.

## 5. Required input bindings

Before evaluation the Validator must recompute and match:

- pre-implementation baseline manifest hash and independent anchor hash;
- its own executable raw-byte hash;
- Validator Registry hash and Registry anchor hash;
- validation authorization record hash;
- real audited-root canonical identity plus approved storage identity or guarded fallback;
- Scope Spec and Ignore Spec hashes;
- Origin and Approved Materialized Registry hashes;
- pre-BUILD authorization anchor;
- Freeze Manifest and freeze-hash anchor;
- current evidence log and newest applicable evidence-chain-head anchor;
- each declared hash above is recomputed from an explicit absolute source path supplied in `binding_source_paths`; request-declared hashes are comparison values only and never an oracle;
- storage identity evidence is independently hashed and its recorded kind/value must match the result binding; the resolved audited-root path is derived again from the declared root;
- the evidence log is replayed record-by-record and the newest applicable evidence-chain-head anchor must value-match `last_sequence_number`, `last_record_hash`, and `log_byte_length`, not merely carry the correct role;
- `binding_source_paths` also supplies the ordered append-only `evidence_chain_anchor_paths`; the Validator verifies every anchor self-hash and `prior_anchor_hash` link and requires the final path to be the authorized current head;
- immutable RT bundle path, complete file inventory, hashes, lineage, branches, producer, and custody evidence;
- result self-hash, stored result payload hash, evidence-record hash, and post-result chain-head anchor.

Command-line paths never override a conflicting authorized binding. Missing prerequisite or required `BLOCKED`/`UNVERIFIED` input yields NOT_READY unless a stronger detected violation requires FAIL. Hash, identity, authority, mutation, tamper, or protection mismatch yields FAIL using the existing contract error vocabulary.

## 6. Audited-root identity

Preferred storage identity is Windows volume serial plus stable file ID, or POSIX device plus inode. Where unavailable, `CANONICAL_PATH_PLUS_GUARD` is permitted only with an explicit reason, reparse/symlink inspection, available volume identity, identical anchored Scope/Ignore inputs, and complete before/after snapshots.

Failure to establish an approved identity is NOT_READY. Identity contradiction or root drift is FAIL. The Validator never writes to the audited root.

## 7. RT-01 through RT-38

The Validator independently recomputes every RT from source artifacts and live read-only observations. Builder `pass`, `RESULT`, `RT_PASS`, `RT_FAIL`, or equivalent fields are comparison metadata only and never oracle inputs.

RT-01..RT-24 retain V1.1.2 semantics. RT-25..RT-30 retain V1.1.3 semantics. RT-31..RT-38 retain V1.1.4 semantics. All identifiers occur exactly once.

RT-34, RT-35, and RT-37 negative branches remain isolated. Negative evidence cannot authorize or replace a positive branch. An RT-35 mutated branch must be retired or complete a new STOP WRITING / Snapshot A / Snapshot B / Freeze sequence before positive reuse. RT-38 consumes valid positive state plus isolated negative observations and never stale restored state.

The existing passed baseline and all historical evidence are immutable. This procedure does not authorize a regression rerun.

## 8. Result and state model

The result conforms to `v1.1.4-validator-result.schema.json` and is a Section 9 `AUDIT_RESULT` class.

- Validator verdict: `PASS | FAIL | NOT_READY`.
- Gate/RT states: `PASS | FAIL | BLOCKED | UNVERIFIED`, with `N/A` only where the contract permits it for gates.
- Cycle-cap orchestration: `ESCALATION_TO_HUMAN`.

`BLOCKED` and `UNVERIFIED` are never collapsed into PASS or silently converted to FAIL. A cycle cap makes the Validator verdict NOT_READY and the contract/orchestration state `ESCALATION_TO_HUMAN`.

For `FINAL_PASS_VALIDATION`, every Section 2 atom/count must appear exactly once, be current for the same lineage, and have checkable evidence. There are no implicit true or zero defaults.

The result schema does not redefine the Section 13 evidence record. After result serialization, its exact stored bytes become a Section 13 payload. The schema also does not add or redefine a Section 24 RC-manifest field.

## 9. Canonicalization and hashing

All contract JSON uses RFC 8785 JCS, UTF-8 without BOM, and exactly one terminal LF. Hashes are lowercase SHA-256 over complete stored bytes including that LF. Result self-hash is SHA-256 over canonical bytes of the result without `result_sha256`, plus the terminal LF.

Before processing evidence, the executable must pass fixed known-answer vectors:

| Logical value | Exact stored SHA-256 |
|---|---|
| `null` | `38e0b9de817f645c4bec37c0d4a3e58baecccb040f5718dc069a72c7385a0bed` |
| `{}` | `ca3d163bab055381827226140568f3bef7eaac187cebd76878e0b63e9e442356` |
| `{"b":1,"a":"x"}` | `b9726bbcdf05823038cfdf7612b50329709a519a5da6f1ac21671f6b5dd31dc2` |
| `{"z":"UTF-8","a":[true,false,null]}` | `817e009ac64b1edad823dcdbdb94c1b4354adf745e42d333a2196abfc71dafae` |

The Validator also checks permitted-domain compatibility with the existing regression library without importing or modifying it. If RFC 8785 and the existing library would serialize an accepted input differently, the input is rejected as `FINAL_PASS_INPUT_INVALID`.

## 10. Evidence and immutability

The result is serialized outside audited scope. Its full stored bytes receive a separate payload hash and are appended through the unchanged Section 13 evidence-record schema. A new independent chain-head anchor is required before the result can support authoritative PASS.

No earlier record, anchor, result, audit, or history is edited. Missing or invalid result anchoring prohibits authoritative PASS. Evidence mismatch maps to `EVIDENCE_TAMPERED`; chain-head mismatch maps to `EVIDENCE_CHAIN_HEAD_INVALID`.

## 11. Fail-closed behavior

- Violation, tamper, mutation, invalid anchor, identity mismatch, protection breach, or failed required RT: FAIL.
- Missing authorization, missing required evidence, unresolved prerequisite, BLOCKED, or required UNVERIFIED without a stronger failure: NOT_READY.
- Cycle limit: NOT_READY plus `ESCALATION_TO_HUMAN`.
- PASS: all applicable required gates and RT-01..RT-38 PASS, with current bound evidence.

Unhandled execution errors exit nonzero and cannot produce an authoritative result. Diagnostic text must not invent a new authoritative error code.

## 12. Self-test limitation

The self-test may use only newly created synthetic temporary fixtures. It must state:

```text
AUTHORITY = NON_AUTHORITATIVE
MAY_SET_CONTRACT_GATE = NO
MAY_SET_RT_RESULT = NO
MAY_SET_FINAL_PASS = NO
MAY_SET_PV = NO
MAY_SET_RC = NO
MAY_SET_STABLE = NO
MAY_SET_HUMAN_APPROVAL = NO
```

It must not read/write a historical lineage, invoke the existing regression harness, or create/activate a Validator Registry.

## 13. Preconditions for first authoritative execution

All are required:

1. Exact passed RT bundle identity, inventory, hashes, lineage, and custody.
2. Human-approved ACTIVE Validator Registry containing the final executable hash.
3. Independently anchored Registry with verified Builder-write exclusion.
4. Approved external evidence/result/anchor locations.
5. Execution authorization naming exact Clean/Dirty/negative branch scope.
6. Approved audited-root storage identity or guarded fallback.

Until then:

```text
REGISTRY_STATUS = PENDING | NOT_CREATED
FIRST_VALIDATOR_EXECUTION_STATUS = NOT_AUTHORIZED
```
