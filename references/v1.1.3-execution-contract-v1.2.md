# PROJECT-INITIALIZATION V1.1.3 — Execution Contract V1.2

Status: PRE-IMPLEMENTATION AUDIT CANDIDATE
Builder Authorization: NO
Authority: this contract defines machine-evaluable execution and PASS conditions for the V1.1.3 proposal.

## 1. Authority model
Human: requirement confirmation, blocking clarification, default delegation, Proposal/Contract approval, Contract Change approval, escalation, Stable release approval.
Builder: implementation, self-test, evidence production, remediation; cannot calculate or announce authoritative FINAL_PASS.
Validator: deterministic facts and gate status.
Independent Auditor: independent implementation/evidence review; read-only.
Final Auditor: verifies contract, evidence chain, Validator, Independent Audit, Production Validation, and release conditions.
Independent Auditor and Final Auditor must not be the same agent instance.
Validator is not self-selected by Builder and must not be the Builder agent instance or execute under Builder-controlled identity. Its identity must be ACTIVE, for the approval_scope covering the execution, in the applicable approved external Validator Registry defined in Section 12 before the BUILD or validation authorization under which it executes. A Validator is authorized only within its recorded approval_scope and only for executions whose authorizing anchor postdates its registration. The registry approver/custodian is independent of Builder.

## 3. Top-level states
PASS, NOT_READY, FAIL, ESCALATION_TO_HUMAN.
Only PASS exits 0. All other top-level states exit nonzero.
Evaluate deterministic errors before state selection. `ESCALATION_TO_HUMAN` applies when any cycle cap is reached. Otherwise, unresolved required user decisions, required `UNVERIFIED`, or missing authorization produce `NOT_READY`; detected contradiction, mutation, tamper, invalid anchor, failed required test, or violated protection produces `FAIL`; and `PASS` applies if and only if `FINAL_PASS == true`. Original V1.1.2 machine-readable gate states remain `PASS|FAIL|BLOCKED|UNVERIFIED|N/A`, with `PROVISIONAL = YES|NO` separate; their mappings are not replaced by these top-level states.

## 4. Clarification contract
Severity: BLOCKING or DEFAULTABLE.
State flow: ASKED → ANSWERED_PENDING_DECISION → CONFIRMED | ACCEPTED_DEFAULT | PENDING_USER_CONFIRMATION | UNRESOLVED.
A user answer is not automatically confirmation of a derived decision.
User silence is not ACCEPTED_DEFAULT.
Classification algorithm, in precedence order: (1) if the decision can affect scope, filesystem design, path contract, ownership, required environment, acceptance/evidence gates, recovery, implementation authorization, protected-preexisting handling, security, destructive action, or overwrite behavior, classify `BLOCKING`; (2) if the decision is not safely reversible, classify `BLOCKING`; (3) only if every prior predicate is false and an exact proposed default exists, classify `DEFAULTABLE`; (4) missing or ambiguous classification input classifies `BLOCKING`. No agent discretion may override this order.
Record: question_id, classification_rule_version, classification_inputs, severity, question, proposed_default, user_answer, delegation_scope, decision, status, affected_artifacts, blocking_gates, evidence_reference, classification_record_sha256.
A classification record uses Section 9 canonical serialization and is immutable once first asked. Reclassification requires the Contract Change Procedure and a new question identifier; reclassification never retroactively legalizes a default.
A required clarification resolves only through CONFIRMED or legitimate ACCEPTED_DEFAULT.
`ACCEPTED_DEFAULT` requires evidence that the Human explicitly accepted that exact default or previously delegated the recorded scope, and the decision falls within it. Default delegation applies only to DEFAULTABLE and never silently covers destructive, overwrite, security, architecture, scope, authorization, recovery, acceptance-gate, or protected-preexisting handling.

Store its canonical bytes and SHA256 in an append-only anchor location outside the audited root, verification workspace, evidence log, and Builder write authority. BUILD authorization is false until Validator verifies this anchor.
Ignore patterns equivalent to **/* are forbidden unless an explicit contract classification permits an empty scope.

## 6. Origin classification
Every relevant object is PREEXISTING, MANAGED_GENERATED, or EPHEMERAL_IGNORED.
An in-scope object without a legal classification is UNEXPECTED_ARTIFACT and blocks PASS.
Before BUILD, scan the real audited root and create `origin-registry.json`, containing every existing relevant object and its Section 8 canonical identity fields plus origin classification and, for PREEXISTING, the V1.1.2 Existing-State classification. Separately create `approved-materialized-registry.json`, containing exactly the objects authorized to be materialized by the current stage and their expected Section 8 identity fields, ownership, and status. Both use Section 9 canonical serialization and are externally approved and anchored using the Section 5 location and authority rules. Their hashes are `origin_registry_sha256` and `materialized_registry_sha256`.
Both registries are immutable from BUILD start. Change requires the same invalidation and return-to-pre-BUILD procedure as Scope/Ignore. Discovery of an unregistered object is evidence of a mismatch, not permission to update a registry.
For `EXISTING_STATE=CLEAN`, after excluding only the externally located Verification Workspace, `ACTUAL_APPROVED_MATERIALIZED_STATE` must equal `APPROVED_MATERIALIZED_REGISTRY` exactly by canonical path, type, and required identity fields; no PREEXISTING entry is permitted. Inequality yields `CLEAN_ROOT_MATERIALIZED_MISMATCH` and `FILESYSTEM_REALITY_GATE_FAIL`.
For `EXISTING_STATE=DIRTY`, PASS requires all V1.1.2 conditions: every approved materialized object exists; every retained PREEXISTING object is in the Existing-State / Origin Registry; there is no UNKNOWN physical path; there is no unauthorized PREEXISTING-to-approved promotion; there is no unauthorized destructive cleanup; and no DESIGNED_FUTURE object is prematurely materialized. The physical root need not equal approved architecture. Any failure yields its original V1.1.2 outcome plus `FILESYSTEM_REALITY_GATE_FAIL`.

## 8. Freeze Manifest
Produce freeze-manifest.json and freeze-manifest.sha256.
Cover every in-scope non-ignored filesystem object in the resolved real audited root, including directories and symlinks. Empty directories are entries. The manifest header records schema_version, audited_root_identity, scope_spec_sha256, ignore_spec_sha256, origin_registry_sha256, materialized_registry_sha256, snapshot_id, and snapshot_time.
Each entry records relative_path, file_type, size, mode, sha256, origin_classification as applicable. `size` and `sha256` are required for files; directory `size` and `sha256` are JSON null; symlink identity uses Section 10 and its non-applicable file fields are JSON null. No field may be omitted based on platform; unsupported `mode` is the documented canonical value `UNSUPPORTED`.
file_type is file, directory, or symlink.
Regular-file SHA256 hashes raw bytes. Directory identity records canonical path/type. Symlink identity follows the symlink contract.
POSIX mode/executable bits are recorded where supported; Windows uses a documented canonical representation and must not invent POSIX semantics.
`freeze-manifest.json` is exactly the Section 9 canonical serialization of PRE_FREEZE_SNAPSHOT_B. `freeze-manifest.sha256` contains the lowercase hex SHA256 of those exact canonical bytes followed by one LF and is recorded both in the evidence chain and in the independent external anchor location. A manifest that differs from Snapshot B is `FREEZE_MANIFEST_INVALID`.

## 9. Deterministic serialization and paths
Canonical paths are project-relative, use "/" separators, and never absolute paths.
All contract JSON (specs, registries, snapshots, manifests, evidence records, anchors, audit results, and RC manifests) uses RFC 8785 JSON Canonicalization Scheme (JCS), encoded as UTF-8 without BOM, with exactly one trailing LF for stored files. SHA256 is computed over the complete stored bytes including that LF and encoded as 64 lowercase hexadecimal characters. JSON numbers are permitted only where JCS represents the value without loss; identifiers, timestamps, modes, and hashes are strings. Arrays whose order has no independent semantic meaning are sorted by canonical path first, then file_type, then canonical serialized bytes; evidence records are the exception and remain append order. Duplicate object keys and duplicate canonical paths are invalid.
PATH_ENCODING is UTF-8. Paths that cannot be losslessly canonicalized, or contain forbidden control characters, produce INVALID_PATH_ENCODING and block PASS; replacement characters are forbidden.
Case-colliding canonical paths produce PATH_CASE_COLLISION and block PASS.

## 10. Symlink contract
Symlinks are not followed by default.
Record relative_path, file_type=symlink, deterministic link_target, and link_target_sha256 over the deterministic target string.
A target outside permitted scope produces SYMLINK_ESCAPE and blocks PASS.
A detected symlink loop produces SYMLINK_CYCLE and blocks PASS.

## 11. Builder STOP WRITING and Freeze establishment
Sequence: Builder self-test → Builder announces STOP WRITING → Validator resolves and records the audited-root identity → Validator scans that real root into `PRE_FREEZE_SNAPSHOT_A` → generate the candidate manifest and all evidence outside the audited root → Validator independently rescans the same root into `PRE_FREEZE_SNAPSHOT_B` → compute the exhaustive A/B diff → only if empty, serialize Snapshot B as the Freeze Manifest and establish FREEZE.
Snapshots A and B use identical scope/ignore anchors, traversal, canonicalization, and Section 8 entry fields. The A/B diff is the sorted union of canonical paths and reports additions, deletions, file-type changes, size changes, mode changes, raw-byte hash changes, origin-classification changes, and symlink-target/target-hash changes. “Equal” means no reported difference; timestamps alone are not identity fields unless a future approved contract adds them to both snapshots.
An empty A/B diff is required for `FREEZE_ESTABLISHED`, `prefreeze_double_snapshot_match=true`, and `builder_write_after_stop=false`. Any A/B difference produces `BUILDER_WRITE_AFTER_STOP`, prevents FREEZE establishment, and cannot be hidden by regenerating A; remediation must begin a new STOP WRITING sequence.
Post-freeze comparison rescans the same resolved real root with the same anchors and checks the complete Section 8 identity. Any protected/in-scope addition, deletion, or identity drift produces `FROZEN_STATE_CHANGED`, sets `freeze_diff_empty=false`, and blocks PASS.

## 12. Validator integrity
Before BUILD authorization, create `validator-registry.json` outside the audited root, Verification Workspace, evidence-log storage, and Builder write authority. Each entry contains validator_id, validator_version, validator_sha256, validator_algorithm_id, validator_runtime, approval_status (`ACTIVE|REVOKED`), approval_scope, approved_by, approved_at, and expiry_or_null. The registry uses Section 9 canonical serialization; an authorized Human approves its hash, and that immutable hash is stored in the independent external anchor location.
Builder cannot create, approve, activate, replace, or mutate a registry entry.
Post-BUILD Validator registration. A Validator whose approval_scope covers post-BUILD validation may be registered after BUILD has started only (a) through the Contract Change Procedure of Section 22, (b) triggered by a discovered Validator-authorization defect, (c) created, approved and anchored by the Human-approved independent registry custodian and never by Builder, and (d) as a new registry artifact whose Section 9 canonical bytes and SHA256 are recorded in a new independent external anchor. Its effect is prospective only: it authorizes only executions whose authorizing anchor postdates the new registry anchor, and MUST NOT validate, re-open, amend, upgrade, or produce PASS for any earlier execution, validation cycle, gate, or evidence record. The prior registry artifact and its anchor remain immutable historical evidence and are never edited, replaced, or deleted.
Applicable registry. For any authorization stage the applicable registry is the newest anchored registry whose anchor predates that stage's authorization anchor. A registry change is a new artifact plus a new anchor; it never rewrites the bytes of a prior anchored registry. A new registry MUST carry forward, with prospective authority, every Validator entry still required by a later stage.
A registry change invalidates Validator approval for subsequent executions and requires Human approval of a new registry anchor; it never retroactively validates earlier evidence.
Every Validator result records the registry hash and all identity fields. Final Auditor verifies the external registry anchor, ACTIVE status and scope/time validity, executable raw-byte hash, algorithm identifier, and runtime before trusting the result. Missing/invalid registry yields `VALIDATOR_REGISTRY_INVALID`; identity or algorithm mismatch yields `VALIDATOR_INTEGRITY_FAIL`. Either blocks PASS.

## 13. Evidence immutability
Evidence log is append-only and hash-chained.
`GENESIS_EVIDENCE_HASH` is 64 ASCII zeroes. Each record contains schema_version, evidence_id, sequence_number, timestamp, evidence_type, payload_hash, previous_evidence_hash, producer, producer_identity_hash, and record_hash. `payload_hash` is lowercase SHA256 over the payload's exact stored bytes. `previous_evidence_hash` is GENESIS for sequence 1 and the immediately prior `record_hash` thereafter. `record_hash = lowercase_hex(SHA256(JCS_UTF8(record_without_record_hash) || 0x0A))`; `JCS_UTF8` means the Section 9 RFC 8785 byte serialization and `0x0A` is the single terminal LF. Sequence numbers begin at 1 and increase by exactly 1; evidence_id is unique. Timestamps are UTC RFC 3339 strings with exactly six fractional digits and `Z`.
The log is a sequence of those canonical one-line JSON records, each terminated by LF. Record order is sequence order and is never sorted. Delete, modify, overwrite, duplicate, reorder, malformed serialization, hash mismatch, or chain break produces `EVIDENCE_TAMPERED`; `evidence_log_immutable=false`; PASS is prohibited.
After every gate-producing append and before each audit handoff, write an `evidence-chain-head-anchor` containing log_id, last_sequence_number, last_record_hash, log_byte_length, anchor_time, producer, prior_anchor_hash, and anchor_hash. The first `prior_anchor_hash` is 64 ASCII zeroes; later values equal the immediately prior `anchor_hash`. Compute `anchor_hash = lowercase_hex(SHA256(JCS_UTF8(anchor_without_anchor_hash) || 0x0A))`, then store the full canonical anchor append-only in an independently controlled location outside the audited root, Verification Workspace, evidence-log storage, and Builder write authority. The Final Auditor compares the newest applicable external anchor to the log and verifies the anchor chain. Absence, replacement, rollback, mismatch, or an unanchored gate-producing tail yields `EVIDENCE_CHAIN_HEAD_INVALID`; `external_chain_head_anchor_valid=false`; PASS is prohibited.

## 15. Auditor read-only enforcement
The auditor must observe the real resolved audited root identified by the Freeze Manifest. Record the root's canonical resolved identity, storage identity where available, access mechanism, audit process identity, commands/reads, and before/after snapshot hashes.
Preferred mechanism is an OS-enforced read-only mount, bind view, sandbox, ACL/token, or equivalent view backed by that same real root. When unavailable, use a before/after full Section 8 snapshot guard over the real root and prohibit all auditor write-capable operations. A detached read-only copy may be supplementary only: Validator must first prove it equals the Freeze Manifest and the audit must still verify the real root before and after; the copy alone cannot set `auditor_observed_real_root=true`.
Audit root is snapshotted immediately before and after audit using the approved Validator. Failure to prove that audit reads addressed the recorded real root produces `AUDIT_ROOT_NOT_OBSERVED`. Any audited-state change during the audit window produces `AUDITOR_WRITE_VIOLATION` regardless of attributed process and blocks PASS; attribution may be recorded but cannot waive the failure.
Audit findings and reports are stored outside audited project scope.

## 16. Verification zero-side-effect
Verification must not auto-fix, mutate through formatters, or write caches/logs into protected audited scope.
Use external temporary locations where practical.

## 17. Remediation ticket and loop semantics
Ticket fields: finding_id, severity, rule_violated, affected_path, evidence_path, expected, actual.
MAX_REMEDIATION_LOOPS = 3.
MAX_VALIDATION_CYCLES = 3 for the approved candidate lineage, including the initial implementation validation attempt.
The initial Independent Audit blocking FAIL establishes the remediation cycle but does not consume a re-audit loop.
Builder fix → new freeze → Validator PASS → Re-Audit.
Each Re-Audit that still returns any Blocking Finding increments remediation_loops by 1, regardless of number or novelty of findings.
Validator FAIL before Re-Audit does not increment remediation_loops; it increments validation_cycles.
Counters start at zero and are external evidence-chain state; they never reset through rename, new freeze, process restart, agent replacement, or finding identifier change for the same approved candidate lineage. A Human-approved Contract Change creates a new lineage with a new lineage_id; the superseded lineage is retained immutable as historical evidence. The change record MUST explicitly record counter carry-forward for the new lineage; unless that record states otherwise, remediation_loops, validation_cycles, and production_validation_cycles carry forward unchanged and are never reset by lineage change, rename, or re-freeze.
When a failed event increments its counter to the applicable maximum, transition immediately to `ESCALATION_TO_HUMAN` and stop automatic remediation/validation. Thus a third blocking Re-Audit or third Validator failure cannot be followed by another automatic attempt. A successful event does not increment a counter.
Non-blocking findings remain in evidence/final report and Human Release Review.

The external anchor must pre-exist the V1.1.3 BUILD and cannot be generated, refreshed, or repaired from V1.1.3 candidate state. Missing anchor yields `V112_EXTERNAL_ANCHOR_INVALID` and prohibits BUILD/PASS.
Validator verifies the anchor and reads the external baseline before BUILD, before each required regression run, and after Final Audit/PV. Exact manifest/inventory mismatch sets `v112_baseline_intact=false` and yields `V112_BASELINE_CHANGED`.
V1.1.3 failure must never damage or overwrite V1.1.2.

## 21. Approval record
Record approved_proposal_version, approved_execution_contract_version, approval_date, approval_scope, proposal_sha256, execution_contract_sha256.
Validator checks approval_record_valid.
Any Proposal/Contract content hash change invalidates the prior approval.

## 22. Contract Change Procedure
Builder may not interpret away, modify, or bypass the contract.
Create CONTRACT_CHANGE_REQUEST with change_request_id, affected_rule, problem, evidence, proposed_change, implementation_impact.
Pause affected implementation → Human Review → if approved, change contract → recompute hash → invalidate old approval → repeat Pre-Implementation Audit → obtain new approval → continue.

## 23. Production Validation
Scenario A: Clean Root.
Scenario B: Dirty Root.
Scenario C: Dirty Root + protected PREEXISTING + Freeze Drift.
Each scenario independently executes Freeze → Verify → Audit and produces independent external evidence.
PV PASS requires A AND B AND C all PASS; no averaging.
PV executor/auditor must not be the main Builder agent instance.
Each scenario records an evidence hash.
A failed scenario returns candidate to implementation/remediation and requires affected candidate re-freeze, verify, and audit.
`production_validation_evidence_hash` is lowercase SHA256 over the Section 9 canonical stored bytes of an object containing candidate_lineage_id and the ordered Scenario A, B, and C evidence hashes; scenario order is fixed as A, B, C.
`MAX_PRODUCTION_VALIDATION_CYCLES = 3`. One production-validation cycle is one ordered execution of all scenarios required for the candidate lineage; a cycle with any failed required scenario increments `production_validation_cycles` once after all safe diagnostic evidence is captured. Successful cycles do not increment it. Counters follow the non-reset and external evidence rules in Section 17.
When the third failed PV cycle increments the counter to the maximum, transition immediately to `ESCALATION_TO_HUMAN` and stop automatic implementation/remediation/PV. No fourth automatic PV cycle is permitted.

## 24. Release Candidate and Stable
`FINAL_PASS=true` and `PV_PASS=true` permit creation of `release-candidate-manifest.json`. It contains schema_version, version=`V1.1.3`, candidate_lineage_id, audited_root_identity, freeze_manifest_sha256, scope_spec_sha256, ignore_spec_sha256, origin_registry_sha256, materialized_registry_sha256, proposal_sha256, execution_contract_sha256, validator_registry_sha256, validator identity fields, v112_baseline_manifest_sha256, rc_input_evidence_head_hash, Independent Audit result hash, Final Audit result hash, ordered Scenario A/B/C evidence hashes, production_validation_evidence_hash, creation_time, and protected_paths. `rc_input_evidence_head_hash` is the external chain-head anchor created immediately after all PV evidence and before RC serialization; no gate-producing append may occur between it and RC creation. `creation_time` is copied from that anchor, not sampled from a new clock, so identical protected inputs serialize identically.
`protected_paths` is the sorted complete union of every in-scope non-ignored path in the Freeze Manifest plus the external specs, registries, manifests, approvals, audit results, PV results, and chain-head anchor identities bound above. External items are represented by stable logical identifier, resolved storage identity, and content hash; they are never expressed as project-relative paths. The RC manifest itself is protected after serialization by `rc_sha256` and the external anchor and is not recursively included in `protected_paths`.
Serialize with Section 9 canonical rules. `rc_sha256` is the lowercase SHA256 over the exact stored canonical bytes including the terminal LF. Store the RC manifest, hash, and evidence-chain head in the independent external anchor location. `RELEASE_CANDIDATE_ID = "V1.1.3:" + rc_sha256`; this is the sole RC identity and is reproducible from the protected inputs.
Any protected-path byte, identity, membership, anchor, bound hash, or later gate-producing evidence append invalidates RC, emits `RELEASE_CANDIDATE_INVALIDATED`, and requires a new freeze/verify/audit/PV as applicable and a new RC manifest/hash. Reusing an invalidated `rc_sha256` is prohibited.
STABLE requires explicit Human approval recording version=V1.1.3, rc_sha256, production_validation_evidence_hash, approval_date, approval_scope, approver.
After Human approval, V1.1.3 becomes STABLE and the new Active Frozen Baseline.
V1.1.2 remains Historical Baseline / Regression Reference and is never deleted or overwritten.

## 25. Rollback
On V1.1.3 failure, continue using V1.1.2 Stable.
Failed candidate artifacts may be retained externally for evidence.
Rollback must not mutate historical V1.1.2.

## 26. Pre-Implementation Audit
Proposal Revision 2 + Execution Contract V1.2 require Independent Pre-Implementation Audit before Builder permission.
Pre-Implementation Auditor must be non-Builder, not the main author agent instance, read-only, and produce structured findings.
Only PRE_IMPLEMENTATION_BLOCKING_FINDINGS=0 permits Proposal APPROVED, Contract APPROVED, and BUILDER_AUTHORIZED=YES.

## 27. Stop-Design Rule
Once V1.1 enters Pre-Implementation Audit, do not proactively add architecture.
Contract changes are justified only by a blocking independent finding, internal contradiction, deterministic implementation impossibility, or clear safety/evidence hole.
Do not continue redesign merely because the system could be more perfect.

## 28. Trust chain
Human Decision → Approved Contract → Verified Builder Output → Approved Validator → Immutable Evidence → Independent Auditor → Final Auditor → Production Validation → Human Stable Approval.
Any critical gate failure prohibits authoritative PASS.
