# PROJECT-INITIALIZATION V1.1.4 — Execution Contract V1.4 Portability Amendment

Status: CANDIDATE — INDEPENDENT REVIEW AND NEW HUMAN APPROVAL REQUIRED

Authority: This amendment incorporates `v1.1.4-execution-contract-v1.3.md` in full and changes only the M1–M5 portability interpretation below. If a V1.3 sentence conflicts with this amendment, this amendment controls. All other V1.3 rules, atoms, error mappings, cycle limits, contract:206, contract:207, RT-37/non-retroactivity, append-only evidence-chain requirements, and approval gates remain unchanged.

## P1. Write authority is a logical authority boundary (M1)

`Builder write authority` means the logical role authority boundary and authorized write set granted to the Builder for the governed lineage. It is not an OS permission domain. “Outside Builder write authority” means the artifact is not authorized to be produced, approved, replaced, mutated, or re-anchored by the Builder role or Builder agent instance. It does not, by itself, require a separate OS account/user, Windows SID, POSIX UID, ACL, mount namespace, filesystem owner, process token, or host.

Filesystem location alone never establishes exclusion. An artifact in an external directory still fails when its producer or approver is the Builder role or the same agent instance that performed the governed BUILD.

## P2. Portable verified Builder-write exclusion (M2)

Default-profile PASS for Builder-write exclusion requires all of the following:

1. the producer/approver is a recorded non-Builder role and has a recorded logical identity and agent-instance identifier distinct from the Builder agent instance;
2. the approved bytes and every referenced custody/evidence byte are immutable for the governed decision and hash-bound by canonical SHA-256 records;
3. the authorizing anchor and its bound approval predate the governed BUILD or authorization stage; a later anchor is prospective only;
4. an append-only hash chain records the approval/evidence and protected-location snapshots taken immediately before and after the governed operation match; any addition, deletion, replacement, or byte/identity drift in a protected location fails the guard; and
5. the Final Auditor independently replays the hashes, timing, logical identities/agent instances, authorized write sets, chain links/head, and before/after protected-location snapshots.

A claim, path, role label, or `builder_write_authority=false` boolean without this evidence is insufficient. OS-level enforcement is not required for default-profile PASS.

## P3. Independent custody (M3)

Independent custody means role separation, recorded approval, hash binding, and non-retroactivity. Directory location alone is insufficient. OS-account separation alone is also insufficient. Custody remains invalid if the Builder authored or approved the anchor, if the custodian is the Builder agent instance under another label, if bound bytes are mutable/unhashed, if the anchor postdates the governed BUILD, or if the append-only/snapshot detection guard is absent or fails.

## P4. Optional high-assurance isolation (M4)

A separate OS user/SID/UID, ACL or token restriction, read-only mount/bind view, sandbox, separate host, or equivalent isolation is `OPTIONAL_PREFERRED_HIGH_ASSURANCE` evidence where available. Its verified presence sets `high_assurance_isolation=true`. Its absence sets `high_assurance_isolation=false` and `assurance_profile=PORTABLE_DEFAULT`; absence alone MUST NOT block PASS when P2 and P3 pass. A claimed but contradicted or bypassed isolation mechanism remains a protection failure.

## P5. Identity means logical agent-instance identity (M5)

Unless a field explicitly says `os_identity`, `security_identity`, `separate identity`, `Builder-controlled identity`, and Validator/Auditor identity fields in this contract mean a recorded logical identity including role, stable identity-record hash, and agent-instance identifier. They do not require a different OS user account. The same OS identity may execute distinct authorized logical role instances. The same agent instance MUST NOT act as both Builder and Validator, Independent Auditor, or Final Auditor where separation is required, even if it changes role labels, process IDs, sessions, directories, or OS accounts.

## P6. Portable audit/read-only wording

Section 15’s before/after full Section 8 snapshot guard is a complete default-profile enforcement path, not merely an exception of last resort. OS-enforced read-only views remain preferred high-assurance evidence. Audit PASS additionally requires the P2 detection guard over every protected external control-plane/anchor location relevant to the audit, with any observed write producing the existing protection/tamper failure.

## P7. Result and regression obligations

Validator results record `builder_logical_identity`, `validator_logical_identity`, both agent-instance identifiers, `os_identity_relationship` (`SAME|DIFFERENT|UNKNOWN`), `assurance_profile` (`PORTABLE_DEFAULT|HIGH_ASSURANCE`), `high_assurance_isolation`, the logical authorized-write-set binding, protected-location before/after snapshot hashes, append-only chain/head verification, and Final-Auditor re-verification requirement.

Regression coverage MUST prove: same OS identity plus distinct authorized logical roles/agent instances can PASS; the same agent instance as Builder and Validator fails; a Builder-authored external file fails; a post-BUILD anchor fails under RT-37; absent OS isolation alone does not block PASS and records non-high-assurance; a protected-location write is detected; and existing evidence-tamper and chain-head negatives still fail.

## P8. Change-control gate

This amendment changes the governing contract hash. Any approval bound to V1.3 bytes is invalid for V1.4. Per Section 22 and Section 26, authoritative use requires Independent Pre-Implementation Audit of the V1.3 base plus this amendment, followed by explicit Human approval recording the new contract and procedure hashes. The Builder cannot create that approval.
